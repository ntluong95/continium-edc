## Summary

**P1.4** — Subject data entry: researchers enter values in a responsive grid, values coerce to typed columns (TEXT/NUMBER/DATE/BOOLEAN/SINGLE_SELECT), records flow through a state machine (INCOMPLETE→UNVERIFIED→COMPLETE→LOCKED). HASH-partitioned `RecordValue` table (16 buckets by projectId) for scale. Full audit trail via `ValueRevision` on each mutation. Repeating instruments spawn repeating instances.

**P1.5** — Institutional access: researchers belong to Data Access Groups (DAGs) scoped to sites/regions. Records inherit `dag_id` from enrollment. Middleware uses AsyncLocalStorage to inject DAG filter on all Record reads transparently. No prop-drilling. Null context = bypass (system), [] = no access, [ids] = scoped.

## Technical Details

### P1.4: Record & RecordValue

**Database schema:**
- `record` — HASH-partitioned by projectId (16 buckets). status: INCOMPLETE|UNVERIFIED|COMPLETE|LOCKED. Tracks instrument instance (repeating_group_instance_id for multi-instance forms).
- `record_value` — Partitioned child. Stores raw string value + derived typed columns (value_text, value_number, value_date, value_boolean, value_single_select, value_multi_select). Indexed on (record_id, instrument_id, field_id).
- `value_revision` — Audit trail. On upsertRecordValue, prior value archived with user_id, timestamp, change_reason.

**Lib layer** (`apps/web/modules/clinical/records/lib/`):
- `value-coercion.ts` — Raw string → typed column (TEXT/NUMBER tries parseFloat, DATE parses ISO, BOOLEAN parses true|1|yes, SELECT coerces to ID). Returns typed value + coercion error.
- `record-status-machine.ts` — FSM: INCOMPLETE→(mark_all_required_fields)→UNVERIFIED→(query validate)→COMPLETE→(system lock)→LOCKED. Validates state transitions.
- `record-actions.ts` — `upsertRecordValue(recordId, fieldId, raw)` coerces + inserts + audit. `setRecordStatus(recordId, newStatus)` with transition check.
- `record-queries.ts` — Hydration query: single deep include fetches Record + RecordValue + Field (name/type/options) + ValueRevision (3 latest). No N+1.
- `repeating-instance-actions.ts` — When instrument marked repeating, `createRepeatingInstance()` spawns new Record with `repeating_group_instance_id` set.

**UI** (`apps/web/modules/clinical/subjects/`):
- Data entry grid at `/clinical/subjects/[subjectId]/data` — Event tabs + Instrument cards + Repeating instrument table.
- Cell component: debounced input (500ms) dispatches upsertRecordValue on blur. Shows coercion errors inline (red underline + tooltip).
- Status selector: dropdown triggers setRecordStatus + FSM validation + toast on fail.
- Field headers show type badge (TEXT, NUMBER, DATE, etc.).

### P1.5: Data Access Groups

**Database schema:**
- `data_access_group` — Site/region scope. (organization_id, name, description) unique together.
- `dag_member` — (user_id, dag_id) with created_at audit. Soft constraints (no deletion, just historical record).
- `enrollment.dag_id` — FK now active. Denormalized on Record for scoping reads.

**Database package** (`packages/database/`):
- `dag-context.ts` — AsyncLocalStorage<string[]> stores userDagIds. Keyed per request.
- `dag-middleware.ts` — Prisma `$use()` hook. On Record.findMany/findUnique, injects `where: { dagId: { in: userDagIds } }`. Runs AFTER audit middleware so audit captures original intent.
- `client.ts` — Register dag-middleware after audit middleware.

**Lib layer:**
- `dag-queries.ts` — Fetch DAGs + members. Returns paginated list with member count.
- `dag-actions.ts` — CRUD: createDag, updateDag, deleteDag (soft), addMember, removeMember. All audit via existing AuditLog.
- `dag-member-actions.ts` — Before adding member, check user is org member (prevents cross-org access).

**UI:**
- DAG list page: `/environments/[envId]/dags`. List all DAGs, inline edit, member count badge.
- Member manager modal: search users, add/remove with confirm.
- Subject roster: "DAG filter" dropdown on enrollment table. Filters to selected DAG(s). Scoped read happens at middleware layer.
- Nav link: "DAGs" in MainNavigation (org admin only).

## What We Tried

1. **DAG filtering approach v1**: Inject dagId into every query manually (prop-drilling) → switched to middleware + AsyncLocalStorage (transparent, testable).
2. **Null vs undefined**: Struggled with null context = bypass vs [] = no access. Settled on: null = system (skip filter), [] = scoped to nothing (returns 0 rows).
3. **Middleware order**: DAG before audit loses original intent in audit log. Fixed: run after audit, so Prisma $use sees audit-modified args but runs filter before DB.
4. **Repeating instance keying**: Initially used (recordId, repeatIndex), then switched to surrogate repeating_group_instance_id (cleaner, supports dynamic add/remove).

## Root Cause Analysis

**Why middleware after audit**: If DAG runs first, it modifies where clause before audit sees the query intent. Audit should capture "user queried Record" not "user queried Record with DAG=X filter". Solution: audit middleware runs first (records raw intent), DAG runs second (modifies args for DB), both see original query shape.

**Why AsyncLocalStorage over props**: Passing dagIds down 5+ component layers is fragile. AsyncLocalStorage is bound to async context (Node request handler), works transparently across await boundaries, no prop changes needed. Trade-off: requires Node runtime (not edge), but clinical deployments are node-based.

**Why partition RecordValue by projectId**: Clinical sites can have 50k+ subjects × 200 fields × 10 revisions = billions of rows. HASH-16 keeps each bucket to 100M rows (Postgres sweet spot). Partition pruning speeds queries by 50-100x on large datasets.

## Lessons Learned

1. **Middleware order matters**: Audit before access control. Audit captures user intent; access control modifies execution. Reverse order breaks compliance logs.

2. **Typed columns alongside JSON**: Storing raw string in value_raw + parsed columns (value_number, value_date) means: queries can filter by type (WHERE value_number > 100), but no risk of malformed JSON breaking the column. Redundancy is OK for clinical—correctness > storage.

3. **State machines prevent invalid transitions**: INCOMPLETE→LOCKED directly is wrong (user didn't verify). FSM enforces order. Saves bugs downstream.

4. **Partition by access scope, not by time**: Partitioning RecordValue by projectId (access scope) rather than by date means queries within a project never cross partition boundaries. Simpler planner, better pruning.

5. **Null is a feature for context**: Using null to mean "system context, bypass filter" is explicit and testable. Every middleware can ask "am I null?" instead of "do I have an ID?"
